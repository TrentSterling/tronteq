Building TrontEQ: a zero-latency Windows system EQ in one day

Windows ships no system-wide equalizer. So I built one: a custom Audio Processing Object that runs inline in the audio graph (no virtual cable, no added latency), driven by a Rust GUI. Here is the whole build, including the seven walls between "it compiles" and "I can finally hear it."

by Trent Sterling · 2026-06-03 · Rust + C++ + a lot of Windows audio internals

The idea

I wanted EQ on everything: games, movies, music, the lot. The usual route is a virtual audio cable that pipes the system into an app that processes and plays it back, but that adds a buffer hop and latency I did not want. The right tool for "zero added latency" is an APO (Audio Processing Object): a COM DLL that Windows loads straight into audiodg.exe and runs inline on the audio graph. The only cost is the math itself.

The plan: a C++ APO doing the DSP, a Rust GUI to draw the curve, and a shared memory-mapped file as the wire between them. The APO reads parameters every buffer; the GUI writes them on every drag. Simple on paper.

Seven walls

The APO compiled, signed, and installed on the very first try. It also did absolutely nothing. Getting from there to audible was a chain of seven separate, individually-silent failures. Each one looked like the last one ("still no sound"), which is what made it fun.

  1. The installer panicked on its own CLSID

    Symptom: install crashed with "Invalid GUID string."

    Fix: windows-core's From<&str> for GUID wants the bare 36-char form; my CLSID had braces (38 chars), so the assert blew up. And because only From is implemented, try_into() could not return an error, it just panicked. Strip the braces.

  2. The APO loaded as COM, never as an effect

    Symptom: registered fine, zero effect on audio.

    Fix: the engine only hosts an endpoint effect that implements IAudioSystemEffects2. Mine exposed only the bare IAudioProcessingObject interfaces, so Windows treated the CLSID as a plain COM object and walked away.

  3. Loaded, but silent

    Symptom: the DLL was finally in audiodg, but it could not read its own settings.

    Fix: APOs run inside audiodg under a restricted token. The settings file needed an ACL grant for ALL APPLICATION PACKAGES, otherwise the APO fell back to its bypassed default. (Diagnosing this was its own saga: audiodg is a protected process, so it cannot write a log file and its debug output never reaches a normal listener. The reliable signal turned out to be a sharing-lock test on the DLL.)

  4. The effect was written to the wrong registry store

    Symptom: "install succeeded," but the CLSID was nowhere the engine looks.

    Fix: setting PKEY_FX_StreamEffectClsid through IMMDevice::OpenPropertyStore writes the endpoint's Properties store. The engine reads effect CLSIDs from the separate FxProperties registry key, which is TrustedInstaller-owned. I had to take ownership and write a plain REG_SZ there.

  5. Still not loading

    Symptom: CLSID in the right slot, still dead.

    Fix: a real APO is also registered under HKLM\SOFTWARE\Classes\AudioEngine\AudioProcessingObjects\{clsid} with metadata (flags, version, connection counts, the system-effects interface IID). Without that registration, the engine never instantiates the CLSID as an APO. This was the big missing piece.

  6. The endpoint slot, and the device toggle

    Symptom: registered everything, restarted the audio service a dozen times, nothing.

    Fix: two things. The right slot for a whole-output EQ is EFX (endpoint effect), not SFX. And an already-connected endpoint only re-reads its effects on real re-enumeration: disable/enable the device, or reconnect it. An audiosrv restart alone is not enough.

  7. Loaded, processing, and muting everything

    Symptom: the APO ran (confirmed!), then killed the audio.

    Fix: APO_FLAG_INPLACE is only a hint. At the endpoint stage Windows hands you separate input and output buffers. My code processed the input and never wrote the output, so the output stayed silent regardless of bypass. Copy input to output, process the output.

"OH fuck I hear it. OW MY EARS."

That was the moment it all came together (I had a deliberately brutal test curve loaded). Seven fixes, each necessary, none sufficient alone.

From an EQ to a processor

Once sound flowed, the EQ alone felt thin. It grew into a full signal chain that audio flows through, each stage toggleable:

Input -> Preamp -> EQ -> AGC -> Compressor -> Limiter -> Output
8 bands 8 filter types (peak, shelves, HP, LP, band-pass, notch, all-pass) preamp compressor (soft knee + makeup) brickwall limiter auto-loudness (AGC)

The AGC is the one I wanted most: it rides a slow gain toward a target loudness, so quiet dialogue comes up and gunshots get caught by the limiter. No more whispers buried under wall-shaking explosions; everything just sits loud.

Polish that made it feel real

Presets on every component

Compressor gets Gentle / Punchy / Crush, auto-loudness gets Subtle / Movie night / Everything loud, the limiter gets ceiling presets, and the EQ gets curve presets (including a "Tinny" one that sounds intentionally awful, great for confirming the thing is actually running). Every section has a reset.

A realtime visualizer

The APO cannot feed audio back to the GUI (that restricted token again). So the visualizer taps the endpoint output directly with WASAPI loopback on its own thread, ring-buffers the samples, and draws a scrolling waveform behind the curve. Zero impact on the audio path.

A theme worthy of an EQ

The whole UI is the tront.xyz electric-cyan look: near-black, a faint grid (which an EQ already is), glowing curve and nodes. There is also a neon rainbow skittles mode, on by default, because why not.

The tray gotcha

Close should hide to the tray, not quit. The catch: eframe's Visible(false) hides the window, but Visible(true) will not bring it back, and while hidden the update loop is asleep so it cannot react anyway. The fix (cribbed from my other tray apps) is raw Win32: grab the real HWND and call ShowWindow / SetForegroundWindow straight from the tray event handler, which fires even while hidden.

Set it and forget it

The icon is my own face (the site favicon, eyepatch and all), baked into the exe. There is a zero-UAC autostart that launches it elevated at logon via a scheduled task. And because the APO lives in audiodg, not the GUI, the processing keeps running whether the window is open, in the tray, or fully quit. You only need the GUI to change something.

How it fits together

Three pieces, one wire:

Rust GUI  --writes-->  C:\ProgramData\TrontEq\state.bin  <--reads--  C++ APO (in audiodg)
   (the editor)            192-byte seqlock mmap                (the always-on processor)

The contract is a 192-byte struct mirrored byte-for-byte in Rust and C++, updated with a seqlock so the realtime thread never blocks. The GUI writes on every drag; the APO reads every buffer. That is the entire integration surface.

What is next

The one thing between this and a public release is code signing: today it needs Windows test-signing mode, which is a non-starter for handing to friends. The fix is a real certificate. The wildcard alternative a friend pitched: port the DSP to an ESP32 and make it a little USB audio dongle with an on-board visualizer, which sidesteps the Windows driver problem entirely and runs on any machine. That one is filed under "helluva moonshot."

Built in a day, mostly at night. TrontEQ is part of TrontStack, a pile of interconnected dev tools and experiments.
